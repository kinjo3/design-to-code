# figma-to-code

Figma のデザインを、対象プロジェクトの規約に沿ってコードに実装し、Figma の書き出し画像との見た目差分が収まるまで調整するスキル。Figma MCP を使えないプロジェクトでは、デザイン画像（スクリーンショットや書き出し画像）を Figma の代わりに入力にできる。実装の規約・トークン・コマンドはこのスキルに持たせず、対象プロジェクトから読む。

## 前提チェック（毎回最初に実行）

### 入力の種類

依頼に含まれる入力で、以降の手順を分ける。

- **Figma URL**: Figma MCP でデザインを取得する。
- **デザイン画像のパス**: Figma MCP を一切呼ばない。同じセクションのブレークポイント別の画像は、1 回の実行でまとめて受け取る。画像は Step 5 で、1 枚ずつ `--figma` にそのまま渡す。`figma-diff.mjs` は PNG しか読めないので、PNG 以外の画像は変換せずに、PNG での提供をユーザーに求める。画像ごとに次の値を受け取る。
  - 表示幅: 画像をキャプチャしたときに、画像に写っている範囲が表示されていた幅（CSS px）。Step 5 で `--figma-width` に渡す。依頼に書かれていなければ、推測せずにユーザーに聞く。画像の px 幅 ÷ 表示幅 が整数にならなければ、ビューポート幅など別の幅を答えている可能性が高いので、ユーザーに聞き直す。
  - ブレークポイント: 画像がどのビューポート幅での表示か。Step 5 で `--width` に渡す。依頼に書かれていなければ、画像はビューポートの全幅を写しているものとして表示幅と同じ値を使い、実装前にその旨をユーザーに伝える。

### プロジェクトの把握

次の項目を読む。見つからない項目は推測で埋めず、実装を始める前にユーザーに聞く。

| 項目 | 読む場所 |
| --- | --- |
| 実装規約（マークアップ・CSS・命名・ファイル配置・ブランチ運用） | プロジェクトの規約。エージェントに読み込まれている指示のほか、README と既存コードの書き方も見る。規約が見当たらなければ、読み取った書き方をユーザーに確認する |
| ビルド・lint・型チェックのコマンド | `package.json` の `scripts`、プロジェクトの規約 |
| デザイントークンの定義ファイル | プロジェクトの規約の記述。無ければ CSS 変数・Tailwind の `@theme`・theme 設定ファイルを探し、見つけたパスをユーザーに確認する |
| 描画先の URL（開発サーバー） | プロジェクトの規約、`package.json`。起動していなければユーザーに起動を頼む |
| 差分チェック・画像計測の依存 | `scripts/figma-diff.mjs` が使う `playwright` `pixelmatch` `pngjs`。デザイン画像の場合は `scripts/design-measure.mjs` も要る。入っていなければ README の導入手順をユーザーに案内する |

### ブランチ

ブランチ運用がプロジェクトの規約に書かれていれば、それに従う。

## Step 1: スコープ確定

- 実装単位の原則: 1 回の実行 = 1 セクション（header、hero、カードリスト等）。ページ全体を一度に扱わない。大きいフレームを渡されたら分割を提案する。
- Figma URL の場合: URL の `node-id` を対象とする。node-id が無い URL なら `get_metadata` でノードツリーを取得し、**どの単位で実装するかをユーザーに確認する**。
- デザイン画像の場合: 画像に写っている範囲を対象とする。Step 5 の差分チェックは画像全体を対象セレクタの描画結果と比べるため、1 枚の画像に複数のセクションが写っていれば、セクション単位で切り出した画像をユーザーに求める。

## Step 2: デザイン取得

### Figma URL の場合

対象 node-id に対して以下を取得する。

- `get_design_context` — レイアウト構造・寸法・色・タイポグラフィの仕様として読む。**返ってくるコード例は特定のフレームワーク向けなので、そのまま貼らない。** 対象プロジェクトのトークンと書き方（Step 3 の対応表と規約）に置き換える。
- `get_screenshot` — 実装時に見比べる見本。スクラッチパッド（`$TMPDIR`）に保存する。
- `get_variable_defs` — Step 3 の対応表の元データ。
- 画像・アイコンがあれば `download_assets`。

### デザイン画像の場合

- 画像を読み、要素の並びと入れ子、文字の太さと書体の見当をつかむ。
- 色と寸法は目で見て決めず、`scripts/design-measure.mjs` で測る。座標と寸法は CSS px で渡し、CSS px で返るので、倍率の換算は要らない。測った値を Step 3 の対応表の元データにする。
  ```
  node scripts/design-measure.mjs --image "<画像のパス>" --figma-width <表示幅> color <x>,<y>
  node scripts/design-measure.mjs --image "<画像のパス>" --figma-width <表示幅> edges row <y>
  node scripts/design-measure.mjs --image "<画像のパス>" --figma-width <表示幅> box <x>,<y>,<幅>,<高さ>
  ```
  - 色: `color` で、塗りの縁から離れた点を測る。縁の画素はアンチエイリアスで背景の色と混ざっている。
  - 部品の位置・寸法・余白: `edges` で、部品をまたぐ行（`row`）や列（`col`）の色の切り替わり位置を測る。角丸の半径は、部品の上端の行と数 px 下の行とで、左端の位置がどれだけ違うかから見積もる。
  - 文字: `box` で 1 行ずつ、文字の外接矩形と色を測る。文字サイズは、大文字か数字 1 字だけを `box` で囲んで高さを測り、書体の cap height（多くの書体で 0.7em 前後）で割って見積もる。1 行全体の高さには b や g のように上下へはみ出す字が入るので、文字サイズの見積もりには使わない。
  - 行高と、文字の上下の余白は、文字の外接矩形だけでは決まらない。同じ文字サイズの行が続いていればその間隔から見積もり、決まらなければ見積もった値で実装して、ずれは Step 5 の調整で合わせる。
- 渡された画像を、実装時に見比べる見本にする。
- デザイン内の写真・アイコンは画像から取り出せないので、ユーザーに素材の提供を求める。提供されなかった部分は、デザインと同じ寸法のプレースホルダーで実装し、Step 7 の未対応点に挙げる。

## Step 3: トークンマッピング

実装前に、デザインの値からプロジェクトのトークンへの対応表を作る。

- 対応表は、デザインの値と、前提チェックで特定したトークンの定義ファイルを突き合わせて作る。デザインの値は、Figma URL の場合は `get_variable_defs` の結果、デザイン画像の場合は Step 2 で画像から読み取った値を使う。
- 既存のトークンを最優先で使う。対応するトークンが無い値は、プロジェクトの規約に沿ってトークンを追加する。追加の規約が無ければ、生値を書かずにユーザーへ確認する。

## Step 4: 実装

マークアップ・CSS・スクリプト・ビルドの規約は、前提チェックで読んだ内容に従う。

## Step 5: ビルド・検証・見た目差分の自動チェック

実装したら必ず実行する。

1. ビルドが必要なプロジェクトでは、前提チェックで確認したビルドコマンドでビルドする（開発サーバーがビルドを監視している場合は不要）。
2. lint・型チェックのコマンドを実行し、エラーを解消する。
3. 上記が通るまで修正 → 再実行を繰り返す。

続けて、デザインとの見た目差分を確認し、収まるまで調整する。

4. 実装したセクション・確認したいブレークポイントごとに以下を実行する（`--width` は表示に使うビューポート幅、`--figma` は Step 2 で保存したスクリーンショットのパス）。プロジェクトルートで、`cd` や `&&` を前に付けずに単独で実行する。README の導入手順 4 の除外ルールに一致しない形で実行すると、サンドボックス内で動いて Chromium が起動しない:
   ```
   node scripts/figma-diff.mjs --url <描画先の URL> --selector "<対象セレクタ>" --figma "<Figmaスクショのパス>" --width <設計幅>
   ```
   カード 1 枚のようにコンポーネント単位で書き出したスクショと比べる場合は、書き出し幅を `--figma-width` で別に渡す。ページ全体の状態に左右されずにスタイルの一致を確認できる:
   ```
   node scripts/figma-diff.mjs --url <描画先の URL> --selector "<カードのセレクタ>" --figma "<書き出したカードのパス>" --width 1440 --figma-width <書き出し幅>
   ```
   固定ヘッダーのように Figma の書き出しには無い要素が対象の上に写り込む場合は、`--hide` で隠す:
   ```
   node scripts/figma-diff.mjs --url <描画先の URL> --selector "<対象セレクタ>" --figma "<Figmaスクショのパス>" --width <設計幅> --hide "<固定ヘッダーのセレクタ>"
   ```
5. `pass: false` の場合は、原因を特定して該当箇所の実装（余白・位置・色等）を調整する。原因は、差分クラスタのテキスト（座標・差分量）と `compare.png`（figma / actual / diff を縮小して横に並べた画像）を併せて読んで探す。原寸画像 3 枚（`figma.png` / `actual.png` / `diff.png`）は、`compare.png` では判断できない微差を詰めるときだけ読む。調整しても `diffRatio` が改善しなかったときは、その調整を元に戻し、別の原因を考えてから次の調整をする。
6. 実装を調整したら、**ビルドが必要なプロジェクトではビルドしてから**、同じ `figma-diff.mjs` のコマンドを再実行する。ビルドしないと変更が反映されず、調整前と同じ差分を測ることになる。
7. 調整と再実行は最大 3 回まで。3 回目の調整後も `pass: false` なら打ち切り、差分画像一式と各回の `diffRatio` の推移を Step 7 の報告に含める。この場合だけユーザーの判断を仰ぐ。
8. フォントの描画などの環境差は、`--threshold`（既定 2%）に収まる前提とする。閾値すれすれの差や、環境差が原因と明らかな差分は、無理に詰めない。

対象外:

- 状態系（hover / focus / active 等）。初期表示状態のみを対象とする。
- 自動切替・トランジションを持つ動的セクション。この種のセクションでは `--wait` を長めに指定するか、初期表示が安定した静止状態を対象にする。

## Step 6: コード自己レビュー

ビルド・検証が通ったら、分岐元との全差分を読み直し、次の観点で点検する。

- **規約準拠**: プロジェクトの規約（トークンの生値ハードコード、命名、レイヤー・ファイル配置、ファイル追加時に必要な登録の漏れなど）
- **セキュリティ・安全性**: 出力時のエスケープ漏れなど、使用言語・フレームワークの定石。既存のユーティリティを再利用せず同等処理を書いていないか
- **設計**: 責務分割・抽象化・共通化の妥当性。1 箇所でしか使わないものを共通の置き場に置いていないか、逆に重複を放置していないか
- **スコープ**: 依頼セクション外への変更、ビルド生成物の直接編集、デバッグ用の残骸
- **アクセシビリティ**: 見出しレベルの連続性、代替テキスト、リンクとボタンの要素選択

重大度で足切りせずに気付いた点を全部挙げてから、対応要否を判断する。修正したら Step 5（ビルド・lint・型チェック）を再実行する。対応しないと判断したものは、理由を添えて Step 7 の報告に含める。

## Step 7: 報告

以下を報告して終了する。

- 追加・変更したファイル一覧
- トークン対応表（Figma 変数、またはデザイン画像から読み取った値 → プロジェクトのトークン、新規追加したトークン）
- lint・型チェックの結果
- 自己レビューの結果（指摘と対応内容、対応を見送った指摘とその理由。指摘ゼロならその旨）
- 差分チェックの結果（各セクション・ブレークポイントの最終 `pass`/`diffRatio`、3 回の調整で収まらなかったものがあればその旨と差分画像パス）
- 未対応点と理由（フォント未導入、実データ待ち、Figma 側の不整合、素材が提供されずプレースホルダーで実装した箇所など）

各項目は結論だけを 1〜2 行で書く。作業経過の再掲・実装コードの解説・既述内容のまとめ直しは入れない。
