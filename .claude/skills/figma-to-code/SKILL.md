# figma-to-code

Figma のデザインを、対象プロジェクトの規約に沿ってコードに実装し、Figma の書き出し画像との見た目差分が収まるまで調整するスキル。実装の規約・トークン・コマンドはこのスキルに持たせず、対象プロジェクトから読む。

## 前提チェック（毎回最初に実行）

### プロジェクトの把握

次を読み、手元に揃える。見つからない項目は推測で埋めず、実装を始める前にユーザーに聞く。

| 項目 | 読む場所 |
| --- | --- |
| 実装規約（マークアップ・CSS・命名・ファイル配置・ブランチ運用） | プロジェクトの規約。エージェントに読み込まれている指示のほか、README と既存コードの書き方も見る。規約が見当たらなければ、読み取った内容をユーザーに確認する |
| ビルド・lint・型チェックのコマンド | `package.json` の `scripts`、プロジェクトの規約 |
| デザイントークンの定義ファイル | プロジェクトの規約の記述。無ければ CSS 変数・Tailwind の `@theme`・theme 設定ファイルを探し、見つけたパスをユーザーに確認する |
| 描画先の URL（開発サーバー） | プロジェクトの規約、`package.json`。起動していなければユーザーに起動を頼む |
| 差分チェックの依存 | `scripts/figma-diff.mjs` が使う `playwright` `pixelmatch` `pngjs`。入っていなければ README の導入手順をユーザーに案内する |

### ブランチ

ブランチ運用がプロジェクトの規約に書かれていれば、それに従う。

## Step 1: スコープ確定

- Figma URL の `node-id` を対象とする。node-id が無い URL なら `get_metadata` でノードツリーを取得し、**どの単位で実装するかをユーザーに確認する**。
- 実装単位の原則: 1 回の実行 = 1 セクション（header、hero、カードリスト等）。ページ全体を一度に扱わない。大きいフレームを渡されたら分割を提案する。

## Step 2: デザイン取得

対象 node-id に対して以下を取得する。

- `get_design_context` — 構造・数値の仕様として読む。**返ってくるコード例は特定のフレームワーク向けなので、そのまま貼らない。** レイアウト構造・寸法・色・タイポグラフィの「仕様書」として扱い、対象プロジェクトの語彙（Step 3 のトークン対応表と規約）に翻訳する。
- `get_screenshot` — 実装時の見た目リファレンス。スクラッチパッド（`$TMPDIR`）に保存する。
- `get_variable_defs` — トークンマッピングの入力。
- 画像・アイコンがあれば `download_assets`。

## Step 3: トークンマッピング

実装前に、Figma 変数 → プロジェクトのトークンの対応表を作ってから書き始める。

- 対応表: `get_variable_defs` の結果と、前提チェックで特定したトークンの定義ファイルを突き合わせる。
- 既存のトークンを最優先で使う。対応するトークンが無い値は、プロジェクトの規約に沿ってトークンを追加する。追加の規約が無ければ、生値を書かずにユーザーへ確認する。

## Step 4: 実装

マークアップ・CSS・スクリプト・ビルドの規約は、前提チェックで読んだ内容に従う。

## Step 5: ビルド・検証・見た目差分の自動チェック

実装したら必ず回す。

1. ビルドが必要なプロジェクトでは、前提チェックで確認したビルドコマンドでビルドする（開発サーバーがビルドを監視している場合は不要）。
2. lint・型チェックのコマンドを実行し、エラーを解消する。
3. 上記が通るまで修正 → 再実行を繰り返す。

続けて、Figma との見た目差分を自動チェック・自動調整する。

4. 実装したセクション・確認したいブレークポイントごとに以下を実行する（`--width` は表示に使うビューポート幅、`--figma` は Step 2 で保存したスクリーンショットのパス）。プロジェクトルートで、`cd` や `&&` を前に付けずに単独で実行する:
   ```
   node scripts/figma-diff.mjs --url <描画先の URL> --selector "<対象セレクタ>" --figma "<Figmaスクショのパス>" --width <設計幅>
   ```
   カード 1 枚のようにコンポーネント単位で書き出したスクショと比べる場合は、書き出し幅を `--figma-width` で別に渡す。ページ全体の状態に左右されずにスタイルの一致を確認できる:
   ```
   node scripts/figma-diff.mjs --url <描画先の URL> --selector "<カードのセレクタ>" --figma "<書き出したカードのパス>" --width 1440 --figma-width <書き出し幅>
   ```
   固定ヘッダーのように Figma の書き出しには無い要素が対象の上に写り込む場合は、`--hide` で隠す:
   ```
   node scripts/figma-diff.mjs --url <描画先の URL> --selector "<対象セレクタ>" --figma "<Figmaスクショのパス>" --width <設計幅> --hide "<固定ヘッダーのセレクタ>"
   ```
5. `pass: false` の場合、差分クラスタのテキスト（座標・差分量）と `compare.png`（figma / actual / diff の縮小横並び）を併せて読み、原因を特定して該当箇所の実装（余白・位置・色等）を調整する。原寸画像 3 枚（`figma.png` / `actual.png` / `diff.png`）は、`compare.png` の解像度では判断できない微差を詰めるときだけ読む。`diffRatio` が改善しなかった調整は元に戻し、別の仮説を立て直してから次を試す。
6. 実装を調整したら、**ビルドが必要なプロジェクトではビルドを実行してから**再度同じ `figma-diff.mjs` のコマンドを実行する（ビルドを挟まないと変更が反映されないまま同じ差分を計測することになる）。
7. 最大 3 回まで調整・再実行を繰り返す。3 回目も `pass: false` の場合はループを打ち切り、Step 7 の報告に差分画像一式と各試行の `diffRatio` 推移を含めて報告する（この場合のみ人間の判断を仰ぐ）。
8. フォントレンダリング等の環境差は `--threshold`（既定 2%）で吸収する前提。閾値ちょうどの僅差や、明らかに環境差由来と判断できる差分は無理に追い込まない。

対象外:

- 状態系（hover / focus / active 等）。初期表示状態のみを対象とする。
- 自動切替・トランジションを持つ動的セクション。この種のセクションでは `--wait` を長めに指定するか、初期表示が安定した静止状態を対象にする。

## Step 6: コード自己レビュー

ビルド・検証が通ったら、分岐元との全差分を読み直し、次の観点で点検する。

- **規約準拠**: プロジェクトの規約（トークンの生値ハードコード、命名、レイヤー・ファイル配置、ファイル追加時に必要な登録の漏れなど）
- **セキュリティ・安全性**: 出力時のエスケープ漏れなど、使用言語・フレームワークの定石。既存のユーティリティを再利用せず同等処理を書いていないか
- **設計**: 責務分割・抽象化・共通化の妥当性。1 箇所でしか使わないものを共通の置き場に置いていないか、逆に重複を放置していないか
- **スコープ**: 依頼セクション外への変更、ビルド生成物の直接編集、デバッグ用の残骸
- **アクセシビリティ**: 見出しレベルの連続性、代替テキスト、リンクとボタンの要素選択

重大度で足切りせずに気付いた点を全部挙げてから、対応要否を判断する。修正したら Step 5（ビルド・lint・型チェック）を再実行する。対応しないと判断したものは、理由を添えて Step 7 の報告に含める。

## Step 7: 報告

以下をまとめて報告して終了する。

- 追加・変更したファイル一覧
- トークン対応表（Figma 変数 → プロジェクトのトークン、新規追加したトークン）
- lint・型チェックの結果
- 自己レビューの結果（指摘と対応内容、対応を見送った指摘とその理由。指摘ゼロならその旨）
- 差分チェックの結果（各セクション・ブレークポイントの最終 `pass`/`diffRatio`、3 回で収束しなかったものがあればその旨と差分画像パス）
- 未対応点と理由（フォント未導入、実データ待ち、Figma 側の不整合など）

各項目は結論だけを 1〜2 行で書く。作業経過の再掲・実装コードの解説・既述内容のまとめ直しは入れない。
