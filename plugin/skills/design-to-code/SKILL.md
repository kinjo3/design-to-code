# design-to-code

Figma のデザインを、対象プロジェクトの規約に沿ってコードに実装し、要素の配置のずれと見本画像との画素差分が収まるまで調整するスキル。見本画像は、Figma の書き出し画像か、次に述べるデザイン画像を指す。Figma MCP を使えないプロジェクトでは、デザイン画像（スクリーンショットや書き出し画像）を Figma の代わりに入力にできる。実装の規約・トークン・コマンドはこのスキルに持たせず、対象プロジェクトから読む。

## ユーザーへの質問

以降の手順で「ユーザーに聞く」「ユーザーに確認する」とした質問は、`AskUserQuestion` ツールで選択肢を示して聞く。

- 選択肢は、読んだファイルや画像から作る。たとえば表示幅なら画像の px 幅を 1・2・3 で割った値のうち整数になるもの、トークンの定義ファイルなら探して見つけたファイル、実装単位なら `get_metadata` のノードを並べる。勧める選択肢があれば先頭に置く。
- 同じ段階で決める質問は、1 回の呼び出しにまとめる（1 回に 4 つまで）。
- 選択肢を 2 つ以上作れない質問と、ユーザーに作業を頼むこと（開発サーバーの起動、素材や画像の提供）は文章で書く。
- `AskUserQuestion` を使えない実行（`claude -p` など）では、文章で聞く。

## 前提チェック（毎回最初に実行）

### 入力の種類

依頼に含まれる入力で、以降の手順を分ける。

- **Figma URL**: Figma MCP でデザインを取得する。
- **デザイン画像のパス**: Figma MCP を一切呼ばない。同じセクションのブレークポイント別の画像は、1 回の実行でまとめて受け取る。画像は Step 5 で、1 枚ずつ `--design` にそのまま渡す。`design-diff` は PNG しか読めないので、PNG 以外の画像は変換せずに、PNG での提供をユーザーに求める。画像ごとに次の値を受け取る。
  - 表示幅: 画像に写っている範囲の、キャプチャしたときの幅（CSS px）。Step 5 で `--design-width` に渡す。依頼に書かれていなければ、推測せずにユーザーに聞く。画像の px 幅 ÷ 表示幅 が整数にならなければ、ユーザーがビューポート幅など別の幅を答えている可能性が高いので、聞き直す。
  - ブレークポイント: 画像がどのビューポート幅での表示か。Step 5 で `--width` に渡す。依頼に書かれていなければ、画像はビューポートの全幅を写しているものとして表示幅と同じ値を使い、実装前にその旨をユーザーに伝える。

### プロジェクトの把握

次の項目を読む。見つからない項目は推測で埋めず、実装を始める前にユーザーに聞く。

| 項目 | 読む場所 |
| --- | --- |
| 実装規約（マークアップ・CSS・命名・ファイル配置・ブランチ運用） | プロジェクトの規約。エージェントに読み込まれている指示のほか、README と既存コードの書き方も見る。規約が見当たらなければ、読み取った書き方をユーザーに確認する |
| ビルド・lint・型チェックのコマンド | `package.json` の `scripts`、プロジェクトの規約 |
| デザイントークンの定義ファイル | プロジェクトの規約の記述。無ければ CSS 変数・Tailwind の `@theme`・theme 設定ファイルを探し、見つけたパスをユーザーに確認する |
| 描画先の URL（開発サーバー） | プロジェクトの規約、`package.json`。起動していなければユーザーに起動を頼む |
| 差分チェックのブラウザ | `design-diff` が使う Chromium。Chromium が無いと `design-diff` が失敗したら、`design-diff-install-chromium` を実行して入れる |

### ブランチ

ブランチ運用がプロジェクトの規約に書かれていれば、それに従う。

## Step 1: スコープ確定

- 実装単位の原則: 1 回の実行 = 1 セクション（header、hero、カードリスト等）。ページ全体を一度に扱わない。大きいフレームを渡されたら分割を提案する。
- Figma URL の場合: URL の `node-id` を対象とする。node-id が無い URL なら `get_metadata` でノードツリーを取得し、**どの単位で実装するかをユーザーに確認する**。
- デザイン画像の場合: 画像に写っている範囲を対象とする。Step 5 の差分チェックは画像全体を対象セレクタの描画結果と比べるため、1 枚の画像に複数のセクションが写っていれば、セクション単位で切り出した画像をユーザーに求める。
- Step 5 で差分チェックするセレクタと幅の組ごとに、プロジェクトルートで登録する。既存の要素ならここで、新しく作る要素ならセレクタを決めた時点で、遅くとも Step 4 を終える前に登録する。Step 5 で `--design-width` を渡す組は、登録にも `--design-width <表示幅>` を足す。登録した組は、合格するか調整が上限に達するまで、Stop hook が終了を止める:
  ```
  design-target register --session ${CLAUDE_SESSION_ID} --selector "<対象セレクタ>" --width <幅>
  ```
  登録がセッション ID の誤りで失敗したときは、差分チェックの完走を Stop hook で確かめられない旨をユーザーに伝えてから進める。

## Step 2: デザイン取得

### Figma URL の場合

対象 node-id に対して以下を取得する。

- `get_design_context` — レイアウト構造・寸法・色・タイポグラフィの仕様として読む。**返ってくるコード例は特定のフレームワーク向けなので、そのまま貼らない。** 対象プロジェクトのトークンと書き方（Step 3 の対応表と規約）に置き換える。
- `get_screenshot` — 実装時に見比べる見本。スクラッチパッド（`$TMPDIR`）に保存する。
- `get_metadata` — Step 5 の箱の比較に使う。出力の XML をそのままスクラッチパッドに保存する。`instance` ノードの内部は返らないので、対象に含まれる `instance` ごとに `get_metadata` をその id で呼び、出力を別ファイルに保存する（足りないインスタンスは `design-diff` が警告する）。
- 文字の対応表 — `get_design_context` の結果から、文字を持つ要素の `data-node-id` と文字列を `{"<node id>": "<文字列>"}` の JSON にしてスクラッチパッドに保存する。インスタンス内の文字は、コンポーネント呼び出しのプロパティ（`label="…"` など）で渡されるので、インスタンスの `get_metadata` に出る text ノードの id（`I<インスタンス id>;<内部 id>`）に結び付ける。
- `get_variable_defs` — Step 3 の対応表の元データ。
- 画像・アイコンがあれば `download_assets`。

### デザイン画像の場合

- 画像を読み、要素の並びと入れ子、文字の太さと書体の見当をつかむ。
- 色と寸法は目で見て決めず、`design-measure` で測る。座標と寸法は CSS px で渡し、CSS px で返るので、倍率の換算は要らない。測った値を Step 3 の対応表の元データにする。
  ```
  design-measure --image "<画像のパス>" --design-width <表示幅> color <x>,<y>
  design-measure --image "<画像のパス>" --design-width <表示幅> edges row <y>
  design-measure --image "<画像のパス>" --design-width <表示幅> box <x>,<y>,<幅>,<高さ>
  ```
  - 色: `color` で、塗りの縁から離れた点を測る。縁の画素はアンチエイリアスで背景の色と混ざっている。`design-measure` がカラープロファイルの注意を出し、そのプロファイルが sRGB でなければ（macOS のスクリーンショットの Display P3 など）、測った色は表示される色とずれる。この場合は sRGB で書き出した画像をユーザーに求める。
  - 部品の位置・寸法・余白: `edges` で、部品をまたぐ行（`row`）や列（`col`）の色の切り替わり位置を測る。薄い罫線のように背景と色の差が小さい境界で切り替わりが出ないときは、`--tolerance` を下げる。角丸の半径は、部品の上端の行での左端の x と、数 px 下の行での左端の x との差から見積もる。
  - 文字: `box` で 1 行ずつ、文字の外接矩形と色を測る。`box` は範囲の左上の画素を背景の色とみなすので、範囲は中身より一回り大きく取る。文字サイズは、字の高さだけでは決めない。丸い字のはみ出しや、字ごとの高さの違いがあるので、高さには ±1px ほどの幅がある。`box` が「中身の外接矩形」と「薄い縁まで含めた外接矩形」を両方出したときは、その 2 つの高さをサイズの候補の範囲に使う。サイズは 1 行全体の幅で決める。字間 0 の候補サイズで実装し、`design-diff` が出す `actual.png` の同じ範囲に `box` を当てて、見本と幅を比べる。全角字だけの行は、幅 ÷ 字数 が文字サイズに字間を足した値になる。字間は、字間 0 で幅の合うサイズが見つからないときだけ足す。
  - 行高と、文字の行とその上下の部品との余白は、文字の外接矩形だけでは決まらない。同じ文字サイズの行が続いていれば、行どうしの外接矩形の上端の間隔から行高を見積もり、決まらなければ見積もった値で実装して、ずれは Step 5 の調整で合わせる。
- 渡された画像を、実装時に見比べる見本にする。
- デザイン内の写真・アイコンは画像から取り出せないので、ユーザーに素材の提供を求める。提供されなかった部分は、デザインと同じ寸法のプレースホルダーで実装し、Step 7 の未対応点に挙げる。

## Step 3: トークンマッピング

実装前に、デザインの値からプロジェクトのトークンへの対応表を作る。

- 対応表は、デザインの値と、前提チェックで特定したトークンの定義ファイルを突き合わせて作る。デザインの値は、Figma URL の場合は `get_variable_defs` の結果、デザイン画像の場合は Step 2 で画像から読み取った値を使う。
- 既存のトークンを最優先で使う。対応するトークンが無い値は、プロジェクトの規約に沿ってトークンを追加する。追加の規約が無ければ、生値を書かずにユーザーへ確認する。

## Step 4: 実装

マークアップ・CSS・スクリプト・ビルドの規約は、前提チェックで読んだ内容に従う。

## Step 5: ビルド・検証・見た目差分の自動チェック

実装したら必ず実行する。

1. ビルドが必要なプロジェクトでは、前提チェックで確認したビルドコマンドでビルドする（開発サーバーがビルドを監視している場合は不要）。
2. lint・型チェックのコマンドを実行し、エラーを解消する。
3. 上記が通るまで修正 → 再実行を繰り返す。

続けて、デザインとの差分を確認し、収まるまで調整する。差分は、要素の配置のずれと、見本画像との画素差分の 2 つで測る。配置のずれは、Figma URL の場合は要素ごとの箱（位置と寸法）で、デザイン画像の場合は実装側の要素の辺で測る。

4. 実装したセクション・確認したいブレークポイントごとに以下を実行する（`--width` は表示に使うビューポート幅、`--design` は Step 2 で保存したスクリーンショットのパス、`--metadata` は Step 2 で保存した `get_metadata` の XML を対象のものから順に全部、`--texts` は文字の対応表の JSON）。プロジェクトルートで、`cd` や `&&` を前に付けずに単独で実行する。README の導入手順にあるサンドボックスの除外ルールに一致しない形で実行すると、サンドボックス内で動いて Chromium が起動しない:
   ```
   design-diff --url <描画先の URL> --selector "<対象セレクタ>" --design "<見本画像のパス>" --width <設計幅> --metadata "<対象の XML>" --metadata "<インスタンスの XML>" --texts "<文字の対応表>"
   ```
   デザイン画像の場合は `--metadata` `--texts` を付けずに、画像 1 枚ごとに、前提チェックの「入力の種類」で決めた値を `--design` `--width` `--design-width` に渡す:
   ```
   design-diff --url <描画先の URL> --selector "<対象セレクタ>" --design "<デザイン画像のパス>" --width <ブレークポイント> --design-width <表示幅>
   ```
   カード 1 枚のようにコンポーネント単位で書き出したスクショと比べる場合は、書き出し幅を `--design-width` で別に渡す。ページ全体の状態に左右されずにスタイルの一致を確認できる:
   ```
   design-diff --url <描画先の URL> --selector "<カードのセレクタ>" --design "<書き出したカードのパス>" --width 1440 --design-width <書き出し幅>
   ```
   固定ヘッダーのように見本画像には無い要素が対象の上に写り込む場合は、`--hide` で隠す:
   ```
   design-diff --url <描画先の URL> --selector "<対象セレクタ>" --design "<見本画像のパス>" --width <設計幅> --hide "<固定ヘッダーのセレクタ>"
   ```
   素材が提供されずプレースホルダーで実装した要素（Step 2 の写真・アイコン）は、`--exclude` で見本画像と実装の両方の比較から外す。外した画素は `diffRatio` の分母にも分子にも入らず、`diff.png` では青で塗られ、範囲は `summary.json` の `excludedCssPx` に残る。セレクタは複数回渡せる。指定した要素が見つからなければエラーになる:
   ```
   design-diff --url <描画先の URL> --selector "<対象セレクタ>" --design "<見本画像のパス>" --width <設計幅> --exclude "<プレースホルダーのセレクタ>"
   ```
   外してよいのは、素材が提供されずプレースホルダーで実装した要素だけ。色や寸法が合わない部分を比較から外して合格にすることはしない。

   ビルドが必要なプロジェクトでは（開発サーバーがビルドを監視している場合を除く）、上のどのコマンドにも `--build` で前提チェックのビルドコマンドを付ける。`design-diff` が撮影の直前にビルドし、ビルドが失敗すれば差分を測らずに、ビルドの出力の末尾を出して終わる:
   ```
   design-diff --url <描画先の URL> --selector "<対象セレクタ>" --design "<見本画像のパス>" --width <設計幅> --build "<ビルドコマンド>"
   ```
5. `pass: false` の場合は、原因を特定して該当箇所の実装（余白・位置・色等）を調整する。
   - まず `[箱]` の報告を読む。Figma のノードごとに、対応付けた実装側の要素と、実装 − Figma の位置・寸法の差が出る。`ずれ` の行から、どの要素の余白・寸法を何 px 直すかがそのまま決まる。親のずれは子にも同じ値で現れるので、最も外側でずれ始めた要素を直す。`候補が拮抗`・`対応なし` は、要素の過不足や入れ子の違いを疑う。文字の対応表に無い text ノードは幾何で照合されるので、対応が外れていれば対応表に足す。
   - デザイン画像の場合は `[箱]` の代わりに `[辺]` の報告を読む。実装側の要素の辺（背景・枠のある要素は箱の辺、文字は字の外接矩形の辺）ごとに、デザイン画像の同じ位置の近くにある同じ境界との差（実装 − デザイン画像）が出る。位置は画像の左上が原点の CSS px なので、`design-measure` でデザイン画像を測り直せる。`同じ辺` に並ぶ要素は、位置も範囲も同じ辺を持つ入れ子の要素で、どれの余白を直すかは実装を読んで決める。文字の左辺・右辺だけがずれる行は、文字サイズか字間を疑う。境界が見つからない辺は、要素の寸法・角丸・中身がデザインと違うことを疑う。透明な入れ物や背景と同じ色の要素の辺は判定不能として数えず、デザインにあって実装に無い要素も `[辺]` には出ないので、これらは `[画素]` で確かめる。
   - 箱（デザイン画像の場合は辺）が揃ってから `[画素]` を読む。画素差分は、箱や辺では見えない中身のずれ（画像のトリミング位置、色、角丸、書体）を見つけるためのもの。原因は、差分クラスタのテキスト（座標・差分量）と `compare.png`（design / actual / diff を縮小して横に並べた画像）を併せて読んで探す。原寸画像 3 枚（`design.png` / `actual.png` / `diff.png`）は、`compare.png` では判断できない微差を詰めるときだけ読む。
   - 調整しても箱・辺のずれや `diffRatio` が改善しなかったときは、その調整を元に戻し、別の原因を考えてから次の調整をする。文字の差分クラスタが大きいのに、文字の行の外接矩形の幅が見本と合っているときは、文字サイズと字間の取り違えを最初に疑う。太さは、文字サイズが確定してから調整する。
6. 実装を調整したら、同じ `design-diff` のコマンドを `--build` も付けたまま再実行する。`--build` を外すと変更がビルドされず、調整前と同じ差分を測ることになる。
7. 調整と再実行は最大 3 回まで。3 回目の調整後も `pass: false` なら打ち切り、差分画像一式と各回の箱・辺のずれの件数・`diffRatio` の推移を Step 7 の報告に含める。この場合だけユーザーの判断を仰ぐ。登録した組のどれかが、合格も打ち切りもしていないまま終えようとすると、Stop hook が理由を返して終了を止める。そのときは理由に挙がった組の差分チェックを続ける。
8. フォントの描画などの環境差は、`--threshold`（既定 2%）に収まる前提とする。閾値すれすれの差や、環境差が原因と明らかな差分は、無理に詰めない。箱や辺の比較で文字の幅だけがずれる場合も、書体が未導入なら環境差として扱う。

対象外:

- 状態系（hover / focus / active 等）。初期表示状態のみを対象とする。
- 自動切替・トランジションを持つ動的セクション。この種のセクションでは `--wait` を長めに指定するか、初期表示が安定した静止状態を対象にする。

## Step 6: コード自己レビュー

ビルド・検証が通ったら、分岐元との全差分を読み直し、次の観点で点検する。

- **規約準拠**: プロジェクトの規約（トークンの生値ハードコード、命名、レイヤー・ファイル配置、ファイル追加時に必要な登録の漏れなど）
- **セキュリティ・安全性**: 出力時のエスケープ漏れなど、使用言語・フレームワークの定石。既存のユーティリティを再利用せず同等処理を書いていないか
- **設計**: 責務分割・抽象化・共通化の妥当性。1 箇所でしか使わないものを共通の置き場に置いていないか、逆に重複を放置していないか
- **スコープ**: 依頼セクション外への変更、ビルド生成物の直接編集、デバッグ用の残骸
- **アクセシビリティ**: 見出しレベルの連続性、代替テキスト、リンクとボタンの要素選択

重大度で足切りせずに気付いた点を全部挙げてから、対応要否を判断する。修正したら Step 5（ビルド・lint・型チェック）を再実行する。対応しないと判断したものは、理由を添えて Step 7 の報告に含める。

## Step 7: 報告

以下を報告して終了する。

- 追加・変更したファイル一覧
- トークン対応表（Figma 変数、またはデザイン画像から読み取った値 → プロジェクトのトークン、新規追加したトークン）
- lint・型チェックの結果
- 自己レビューの結果（指摘と対応内容、対応を見送った指摘とその理由。指摘ゼロならその旨）
- 差分チェックの結果（各セクション・ブレークポイントの最終 `pass`、箱・辺のずれの件数、`diffRatio`。3 回の調整で収まらなかったものがあればその旨と差分画像パス）
  - 収まらなかった箱・辺のずれは、件数だけではユーザーがどこを見ればよいか分からないので、どこがどうずれているかを 1 つずつ書く。この一覧は下の「1〜2 行」に含めない
  - 要素は、ユーザーが画面で探せるよう、見た目や文字の内容で呼ぶ。クラス名と座標は書かない。ずれの向きと量を添える（例:「表の各行のチェックボックスが、デザインより 3px 上にある（11 か所）」「『Checking ****1842』の文字が、デザインより 4px 狭い」）
  - 同じ要素の同じずれは 1 つにまとめ、繰り返す数を「〜か所」で添える
- 未対応点と理由（フォント未導入、実データ待ち、デザイン側の不整合、素材が提供されずプレースホルダーで実装した箇所など）
- 差分チェックの比較から外した要素（セレクタと `summary.json` の `excludedCssPx` の範囲。素材が提供されなかったことが理由）

各項目は結論だけを 1〜2 行で書く。作業経過の再掲・実装コードの解説・既述内容のまとめ直しは入れない。
